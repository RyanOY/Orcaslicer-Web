## 0. 起点：用户的原始构想

> 「基于本机（ARM 飞牛 OS），内置使用 orcaslicer cli 模式进行切片，UI 和图形渲染放到 web 端调用手机 GPU 资源。」

一句话里其实有四个独立假设，需要逐个验证：

1. OrcaSlicer 有 CLI 模式，能切片
2. ARM64 上能跑
3. Web 端做 UI
4. 渲染放到手机 GPU

---

## 1. 事实核查（2026-10-28 实测/查证）

### 1.1 OrcaSlicer CLI —— 成立，且比预想的强

官方 Wiki 有完整的 [CLI Mode](https://www.orcaslicer.com/wiki/cli/cli_mode.html) 文档（2026 年补全）。

**支持的切片相关动作：**

| 类别 | 参数 |
| --- | --- |
| 动作 | `--slice <plate>`、`--export-3mf`、`--export-slicedata`、`--export-stl`、`--export-settings`、`--info` |
| 几何变换 | `--arrange`、`--orient`、`--rotate`、`--scale`、`--ensure-on-bed` |
| 配置加载 | `--load-settings "process.json;printer.json"`、`--load-filaments filament.json` |
| 输出 | `--outputdir`、`--logfile` |

**关键发现：任意 GUI 参数都能用 `--key=value` 覆盖。** 键名里的下划线转连字符：

```
layer_height          →  --layer-height=0.2
sparse_infill_density →  --sparse-infill-density=15%
```

多值参数用逗号分隔（`--retraction-length=0.8,0.8,1.2`），有两条坑：值不够会用**第一个值填充**而不是各自默认值；重复传同一个 flag 是**追加**不是覆盖。

**43 个键永远不暴露在 CLI**，主要是三组：preset 身份与继承（`preset_name`、`inherits`、`compatible_printers`…）、打印主机连接（`print_host`、`printhost_apikey`…）、内部挤出机索引。→ **推论：连接打印机的活不能交给 CLI，必须由 UI 侧调 Moonraker 完成。** 这条直接影响了架构分工。

典型调用：

```bash
orca-slicer model.3mf \
  --load-settings "process.json;printer.json" \
  --load-filaments filament.json \
  --arrange 1 --slice 0 --export-3mf out.3mf
```

### 1.2 ARM64 构建 —— 成立

Linux 侧有 **AppImage ARM64** 与 **Flatpak ARM64** 官方构建。

fnOS 上的注意点：AppImage 依赖 FUSE，容器里通常不可用 → 用 `--appimage-extract` 解包后跑 `squashfs-root/AppRun`，或干脆装 Flatpak 版。

### 1.3 手机 GPU 渲染 —— 成立，而且是唯一选择

gcode 预览本质是百万级线段。three.js + WebGL2 在手机上完全够用。

但真正的约束在反方向：**这台 NAS 的 GPU 用不了。** 前面查过，系统里只有未加载的闭源 `mali.ko`，没有 `panthor`，连 GL 加速都不通。所以“服务端渲染 + 视频串流”这条路是物理性死亡。

→ **选手机 GPU 不是优化，是唯一出路。** 收益也不是“渲染更快”（手机 GPU 未必强过桌面），而是**省掉了服务器端渲染和串流带宽**。

### 1.4 实测结果（2026-10-28 已跑完，详见 `spike-results.md`）

| 未知项 | 结论 |
| --- | --- |
| **无 X 环境能否跑通** | ✅ 能，**连 xvfb 都不需要**。`--help` / `--info` / `--slice` 全通 |
| **ARM64 实际切片耗时** | ✅ 120k 面 / 500 层 → **5.5 s**；中等机械件 → 3.7 s；小件亚秒。落在 <30 s 档 → 可做准交互式 |
| **单核还是多核** | ✅ **多核**，失败用例里 CPU 260 s / wall 39 s ≈ 6.7 核 |
| `--export-slicedata` | ❌ 产出空目录，不可用 → 预览必须解析 gcode |
| gcode 体积 | 500 层花瓶 15.7 MB，200 层格栅 9.7 MB → <50 MB 档 |

CPU：机型确认为 **RK3588 级 8 核 = 4×A76@2.4 GHz + 4×A55@1.8 GHz**，7.7 GB RAM。大核存在，实测速率与此吻合。

**新发现的硬约束（原计划没算到）**：fnOS 是 Debian 12（glibc 2.36），官方 aarch64 AppImage 是
Ubuntu 24.04 构建（需 glibc 2.38 / GLIBCXX 3.4.32），**宿主机原生跑不通，且没有更老的 aarch64 构建可选**。
→ 节点必须以容器形态存在，这反过来确认了解耦架构的必要性。

**另有两个 CLI 坑**（已写进 `api-contract.md` 级别的实现约束）：`--export-3mf` 在 2.4.2 aarch64 上直接段错误，
改用 `--slice 0 --outputdir DIR` 取 `plate_1.gcode` + `result.json`；`--load-settings` 指向内置系统 profile
会因 `inherits` 链无法解析而报错，需要 flatten 后的配置。

## 2. 被否决的方案

### ❌ A. 完整复刻 OrcaSlicer GUI 到 Web

工作量在「准备」页，不在切片：

- 支撑刷子 / 接缝刷子 / 颜色刷子 —— 逐三角形数据 + 拾取 + 回写
- 可变层高 —— 沿 Z 的重采样曲线
- 模型切割、布尔运算、装配
- 1000+ 参数的分组面板、依赖关系、联动禁用

这是 3–6 个月的正经项目，且做完就落后上游一个版本，永远追不上。
**结论：不碰。** 只做「常用 10 个参数 + 预设档」。

### ❌ B. 服务端渲染 + 视频串流

见 1.3，GPU 驱动不可用。

### ❌ C. 把 OrcaSlicer 打进 fpk

上游一年一大版，CLI 参数仍在演进（本文档引用的 CLI 文档就是 2026 年才补的）。嵌死意味着每次升级都要重发 fpk 走一遍安装流程，且完全无法换机器。
**结论：解耦。这正是用户后一条需求（见 §3）的来源。**

### ❌ D. 云切片（SimplyPrint / 创想云等）

前面查过：云切片普遍没有 Voron 机型支持，或者要付费 + 把模型传上云。
**结论：否决，但留个口子** —— 因为节点是 HTTP 服务，将来接任何实现同协议的后端都行。

## 3. 关键决策：UI 与切片器解耦

### 用户的补充需求

> 「fpk 只是 UI，切片器通过本机的 docker 安装的 orcaslicer 加载，后续换了电脑也可以接入电脑的 orcaslicer docker 服务端。」

这条把项目从「一个 fpk」变成了「一个协议 + 两个实现」。认同的理由：

1. **升级解耦** —— OrcaSlicer 升级只需 `docker pull` 新节点镜像，UI 不动
2. **算力可迁移** —— NAS 算力不够就把节点搬到 PC，UI 不感知
3. **可多实例** —— NAT 后面放两个节点，按队列路由
4. **可测试** —— 节点可以用 curl 单独验收，不需要前端

### 但要先纠正一个前提

**“OrcaSlicer docker 服务端”并不存在。** OrcaSlicer 是桌面程序，没有网络 API。所谓“服务端”是**我们自己写的一层壳**：容器里 Xvfb + OrcaSlicer CLI + HTTP API + 队列。

所以交付物是两件，不是一件：

```
slicer-node/   多架构镜像（arm64 跑 NAS / amd64 跑 PC），无状态
orca-web/      fpk：静态前端 + BFF 反向代理
```

## 4. 四条一票否决的设计约束

这四条如果开工时不定死，半年后接第二个节点必然返工。

### ① 手机只连 NAS —— 必须做 BFF 代理

节点在 PC 上时，用户在外面用手机根本连不到它。所以：

```
手机 ──HTTPS──▶ NAS(orca-web) ──明文内网──▶ 节点
```

**前端永远只跟一个源说话**，节点地址是后端配置项。不做这条，「换台电脑也能接」在异地场景直接废掉。

### ② 预览由节点生成，不让 UI 解析 gcode

如果节点在 PC、UI 在 NAS，让 NAS 拉 100 MB gcode 再解析，等于把算力又搬回了最弱的那台机器。

节点在切片完成后就地解析，输出**紧凑二进制分层层数据**（每层线段打包成 typed array + 材质类型位），目标体积 ≤ gcode 的 1/20。UI 按层区间拉取，永不下整份 gcode。

### ③ 能力协商，不许假设

UI 启动先打 `GET /v1/capabilities`。老节点没有 `slicedata` 就降级；`orca_version` 决定哪些滑块显示。**协议版本号从第一天就要有**，否则换设备/装旧镜像时前端会白屏而不是报错。

### ④ profile 归节点管

不把 Voron 的 `machine.json` 打进 fpk。profile 是**节点的能力**：PC 上装了什么档，UI 就显示什么。换机器时只需把 profile 目录拷过去。

## 决策记录：层预览为什么长这样（v0.2.1）

### 为什么不把 gcode 丢给前端解析

15 MB 文本、50 万条指令。手机浏览器里解析要几十秒，内存峰值几百 MB，
且每个用户每次打开都要重来一遍。服务端解析一次（2 s，8 核里占 1 核）
固化成 8.3 MB 二进制，之后所有人都只拉自己需要的那几层。

### 为什么每段只存二维

z 在层内是常量。存成 (x1,y1,z,x2,y2,z) 每段 24 字节，现在 16 字节 —— 省 1/3；
shader 里 `vec4(pos, uZ, 1.0)` 一行就还原，没有任何代价。

### 为什么层内要按类型排序

需求是「只看外墙，检查表面质量」。若不排序，前端拿到 1030 段要先建一个筛选索引
（10 万级操作 × 每次过滤），或者服务端每次把整层读出来再筛。
排序后：`ranges[0] = [0,186]`，按 16 字节步长取 186 条连续区间就完事，
服务端两次 seek，前端零计算。代价是构建时多 0.3 s。

### 为什么抽层而不是 RDP 抽稀

先量了才决定：vase 每层 1030 段，即使复杂的机械件也就几千段，
一条 1 万段的分层用 `gl.LINES` 画也就 2 万顶点，GPU 根本不累。
真正的痛点是「看整体」时要下 8.3 MB。所以抽的是层：
`overview_stride=4` → 126 层 2.08 MB；配合「只看外墙」→ 0.38 MB（22 倍差距）。
如果以后真遇到单层 5 万段的模型（超大平面 + 密集填充），再上 RDP 也不迟，
而且那时可以直接对单层做，不影响契约。

### 为什么单层接口不做批量

批量接口（一次要 30 层）看起来省往返，但每层在 bin 里本来就是连续的一段，
`Range: bytes=a-b` 就能一次拿多段 —— 用标准 HTTP 能力，而不是自己造协议。
过滤后的批量确实需要多次请求（因为每段长度不同、要拼接），
但过滤通常只用于「全模型概览」，此时用 stride 只有 126 个请求，
6 并发下总耗时 0.15 s，没必要为它写个自定义帧格式。

## 决策记录：预览 UI 为什么这么写（v0.3）

### 颜色必须和 OrcaSlicer 一致，所以去读它的源码

「和 Orca 一样」最容易走偏的地方就是配色。直接从 OrcaSlicer 的
`src/libvgcode/src/ViewerImpl.cpp` 抄 `DEFAULT_EXTRUSION_ROLES_COLORS`，
八个类型一一对应（见 `slicer-node/README.md` 的表）。
顺手把 `top_surface` 从「实心填充」里拆出来 —— Orca 图例里顶面是单独一色
（红 `#F04040`），混在一起就没法「只看顶面」。

### 线用实例化四边形画，不用 gl.LINES

`gl.LINES` 在大多数实现里固定 1 物理像素、没有抗锯齿、线宽不可控。
手机上 1px 的线在高分屏里细到看不清，在低分屏里又没有层次。
改成每段一个实例化的四边形：顶点着色器把两端投影到屏幕空间算出法向，
按 `uHalfWidth` 像素偏移，片元着色器在法向两侧做 `smoothstep` 淡出。
结果：线宽可控（1.5–1.9px）、边缘干净、每帧只多 6 个顶点/段。

代价是顶点数 ×6，但 vase 全模型 51 万段也就是 300 万顶点 —— 手机 GPU 完全吃得下。

### 过滤放在客户端，服务端的 `?types=` 留给弱网

v0.2 的做法是切换类型就重新请求（省流量）。实际用起来那次请求的往返
比渲染还慢，点一下图例要等 200 ms 才变。
改为：每层全量取回来（18 字节/段），`ranges` 让她在本地按区间画 —— 切换**零延迟**。
服务端的 `?types=` 没删，留给按流量计费/弱网的客户端。

### 「全部层」必须不透明

一开始全部层用 0.32 半透明画，结果像玻璃，还能透过缝隙看见内墙 ——
与 Orca 的观感差很远。Orca 的「全部层」就是不透明实体外壳。
改成不透明 + 深度测试后，外墙占比从 0.5% 跳到 32%，才是实体。
要「看内部」就用「单层」或「累积」，这两种模式才需要透明。

### 拖动时降采样

51 万段 × 6 顶点的全量绘制在低端手机上会掉到 15 fps 左右，手感发粘。
拖动/缩放期间每隔 4 层画 1 层（松手 180 ms 后恢复全质量），
视觉上几乎察觉不到，但帧率回来了。层数据本来就在缓存里，不用重新请求。
## 决策记录：线宽改成物理宽度（v0.3.7）

### 问题

v0.3 的线宽是屏幕像素定宽的（1.5–1.9 px）。后果一：手机上看着极细；
后果二：**墙面永远贴合不上**——同一层两道相邻墙心的间距是 0.45 mm，
在默认取景下约 7 设备像素，而线只有 4 像素宽，中间留一条缝，
本该是「实心带」的墙看起来像几条平行细丝。

### 做法

顶点着色器里按真实挤出宽度换算成像素：

```glsl
float pxPerMm = uProj / max(abs(p.w), 1e-4);      // p.w = 该顶点的视深度(mm)
float halfPx  = clamp(0.5 * uWidthMm * pxPerMm, uMinHalfPx, uMaxHalfPx);
```

`uProj = (视口高/2)/tan(fov/2)`，即画面中心处每毫米对应多少设备像素。
默认 `uWidthMm = 0.45`（0.4 喷嘴的典型挤出宽度），夹在
`[0.8, 4.5] × dpr` 之间：拉远不至于细到消失，怼近了不至于糊成一片。

这样线宽 ≈ 线间距，墙自然连成实心带；放大时线跟着变粗，
和 OrcaSlicer 的观感一致（它就是按挤出宽度画 tube 的）。
底板网格把 `uWidthMm` 置 0，保持纯像素细线。

取景顺带从 `diag × 1.45` 退到 `diag × 1.85`，默认视角别贴脸。

### 双指平移方向

`pan()` 里的相机右向量写成了 `(sin az, -cos az, 0)`，符号反了；
正解是 `(-sin az, cos az, 0)`（= `cross(viewDir, up)`）。所以横向反向、
纵向正常——和用户报的现象完全对得上。
同时把平移改成 1:1 跟手：`scale = 2·dist·tan(fov/2) / 视口高(CSS px)`，
原来用 `dist × 0.0016` 是个拍脑袋的系数，实际跟手速度约快 1.9 倍。

### 顺带修掉

`setPointerCapture()` 在合成事件/部分环境会抛异常，原来它写在 `pointerdown`
最前面，一抛就把整个拖拽初始化跳过了（指针表根本没填）。现在包在 try 里。

### 怎么验证的（无人工目测）

- 线宽：真实切片（240 层小船），读回 framebuffer，统计亮像素数与缩放的关系。
  缩到 0.63 倍时亮像素×0.40 ≈ 0.63²，是「物理宽度」的指纹（像素定宽会是 ×0.63）。
  默认取景实测 6.5 设备像素 = 3.25 CSS px ≈ 0.45 mm × 15.7 px/mm。
- 墙面是否贴合：放大截图的水平扫描线上，游程出现 29/47/50/57/111 px 的长块，
  说明多道墙已经并成实心带，不再是细线加缝。
- 平移：合成双指事件，比对模型像素质心位移。右/下/左三方向都是 +74/+63/−57 px
  （拖 60 px），方向正确且接近 1:1。

## v0.4.2 走线的端帽：别再把圆柱往两端拉

### 问题

v0.4 的管体是「圆柱 + 沿轴两端各延长一个半径」。延长是为了填拐角：
两段在接点各自多出一截，视觉上把楔形缺口盖住。代价是**这截方柱戳出路径**——
路径末端（每条填充线的头尾）冒出一段半径长的方头，90° 拐角外侧留下一个方角，
相邻管子还会互相插进去，从侧面看得到明显的交叉接缝。

### 做法

延长去掉，改成**球冠端帽**：端点就是圆柱端面，端帽是圆心落在端点上、
半径等于半径的半球冠。顶点属性从 `(t, cosθ, sinθ, ±1)` 改成
`(a: 0/1 沿段位置, b: 端帽轴向偏移/r, cosθ, sinθ)`，剖面半径在着色器里解析求：

```glsl
float rho = sqrt(max(0.0, 1.0 - b * b));      // b=0 → 1（柱身），b=±1 → 0（极点）
vec3  pos = mix(p0, p1, a) + ax * (r * b) + radial * (r * rho);
vNrm      = normalize(ax * b + radial * rho); // 球冠/柱身共用一条法向公式
```

端点处 `b = 0`，所以**基网格的端点严格落在 p0/p1 上**，不再有任何沿轴外伸。
相邻两段在同一接点的球冠完全重合，等于「圆角接头」（round join）的下界：
比它缺一点（bevel），绝不会比它多。路径末端则是半圆收口——和真实料条的收尾一致。

### 两套基网格 + LOD

同一个实例数据配两套顶点/索引，只按当前线宽切换：

| 网格 | 圈数 | 三角/段 | 顶点/段 | 用在哪 |
|---|---|---|---|---|
| `thin` | 2（纯柱身） | 16 | 18 | 宽度 < 4.5 设备像素：拐角缺口不足 1 px，看不见，省 3 倍三角形 |
| `caps` | 4（柱身 + 两端球冠） | 48 | 36 | 放大到看清接头时 |

自动模式的段数预算按**当前视图真正要画的段数**分档：细管 160 万段，球冠 20 万段
（≈ 2500 万三角）。注意是「要画的」，不是整份文件：单层视图只算当前层 + 下面两层，
累积视图算 0..当前层。v0.9.3 之前用整份段数（细管 45 万 / 球冠 15 万），
0.16 层高的同尺寸模型段数从 41 万涨到 50 万，直接被判死、只能退回纯线条。
需要时用户仍可手动「体积」强制开。

### 截面要压扁成「宽 = 线宽、高 = 层高」

正圆柱看着像一根根圆丝，但真实的挤出丝是**扁的**（0.4+ mm 宽 × 层高）。
层高 0.2 时圆柱直径只比层高大 2 倍，勉强还行；层高 0.16 时上下层互相插进去 60% 以上，
整摞糊成一块。v0.9.3 起把截面按 `squash = (层高/2) / 半径` 压扁：

```glsl
float halfH = 0.5 * max(uLayerH, 0.02);
center.z -= halfH;                                  // gcode 的 Z 是层顶，丝体在它下面
float squash = clamp(halfH / max(r, 1e-4), 0.10, 1.0);
pos.z = center.z + (pos.z - center.z) * squash;      // 椭圆截面
nrm.z /= max(squash, 0.05);                          // 椭圆法线：z 分量按 1/压扁比放大
```

压扁之后每层正好占满自己的层高，顶面亮、贴下层暗。但**竖直外壁上所有层的侧法线
完全一样**，光照还是给不出一条层线 —— 所以再叠一条「层缝」：层底往上 35% 的范围
压暗 22%。这是纯视觉线索，不参与几何。

### 怎么验证的

合成一段 L 形（宽 0.86 mm，拐角在画面正中，宽 11.5 设备像素），
把 framebuffer 读回来按 1 字符 = 2 px 打成 ASCII：

- 旧版：拐角处是完整的 12×12 px 方块 —— 两个方向各外伸 6 px（= r），即方角。
- 新版：外侧变成半径 6 px 的圆弧，拐角内部没有缺口（90° 时两个半球冠并集够覆盖）。
- 45°/135° 拐角新旧一致（旧版的方角在钝角/锐角上本来就不明显）。

真实数据（240 层小船，70 669 段，第 120 层，强制体积）：

| 取景 | 旧版 | 新版 | 差异 |
|---|---|---|---|
| wpx 8.8（球冠） | 72 013 px / 2 块 / 0 碎屑 | 71 041 px / 2 块 / 0 碎屑 | −1.35 % |
| wpx 3.7（细管） | 23 670 px / 11 块 / 8 碎屑 | 23 425 px / 11 块 / 8 碎屑 | −1.04 % |

亮像素略降（戳出去的部分没了），连通块数与孤立碎屑数完全不变 —— 没有新空洞。

## 着色依据：把机器状态写进每段（v5 索引）

需求是「像 OrcaSlicer 那样按挤出机/速度/风扇/温度/加速度/抖动上色」。
原生数据只有位置、类型、挤出量，别的都得从 gcode 里读。

做法是一台极简的状态机跟工具头段落走：`T` 换工具、`M104/M109` 定喷嘴温度
（`M109` 会阻塞，所以段边界落在它之后）、`M106` 风扇、`M204` 加速度、
`M205 J` 抖动（SP 机器会走 `SET_VELOCITY_LIMIT`，两种都认），
`G1 F` 是这一段自己的速度。开机设过但没再改的值会一路挂着 ——
所以第一层的段也有正确温度，不会出现前半段「未知」。

存储上不按段存六个数（7 万段 × 6 × 2B 就 0.8MB），而是**去重成 attrs 表**，
每段只存一个 Uint16 下标：7 万段 → 295 种组合，段增量 = 2 字节（+11%），
索引多 4KB。前端把「段 → 组合 → 颜色」解成一张 65536 长的映射表，
切依据时只重建这张表（不到 1 ms），几何 buffer 一动不动。

选色策略看取值个数：≤6 种（温度/加速度/抖动/风扇/挤出机）走离散色 + 图例行，
多了（速度，实测 158 种）走连续渐变 + 刻度条，只有一种就整块纯色 ——
跟 Orca 的「按区间配不同色带」是一个思路，阈值按可读性定。

老任务的 v4 段没有 attrs，前端据 `index.version` 和每层字节数判断，
把这几项置灰，绝不画错色。

## 决策记录：前端为什么不单独做 fpk（v0.6–0.7）

最早的架构是「fpk 纯前端 + BFF 反代 slicer-node」，理由是换机器时前端一行不改。
做到 Web UI 时改了主意：**工作台和节点合并成一个容器，同源发页面**。

- 少一跳、少一份配置（节点地址、token、CORS 全都不用管）。
- 摆盘、切片、预览三处都要共享状态（对象列表、bed、profile 选择），同源最省事。
- 「换机器」的需求并没有消失，只是变成「换后端地址」——真要做，加一层反向代理即可，
  不必为此每天付出跨域和两份部署的成本。

原先设想的鉴权（`X-Slicer-Token`）也随之放弃：只在内网用，暴露公网是禁止项。

## 决策记录：3MF 的网格必须内联（v0.8.1）

最初为了「轻」，把每个子部件写到 `3D/Objects/object_N.model`，主文件用
`<component p:path="/3D/Objects/object_N.model" objectid="N"/>` 引用 —— 这是 3MF 规范里
正规的 component 用法。

实测 OrcaSlicer 2.4.2 不按规范来：**它按 `objectid` 在全局 id 空间里查，完全忽略 `p:path`**。
每个外部文件里的对象都叫 `id="1"`，于是全部互相覆盖，切出来 N 个一模一样的部件
（用户看到的「摆盘是两个不同部件，预览里两个一样」）。

改法：所有网格内联进主 `3dmodel.model`，每个对象在文件内有唯一 id，`<build><item>` 直接引用
顶层 `object`；挤出机归属仍写在 `Metadata/model_settings.config`。

代价：3MF 体积变大（网格不再按子文件分开）；换来的是「所见即所切」。
验证方式是 gcode 里的 `EXCLUDE_OBJECT_DEFINE ... POLYGON=`：每个对象的多边形必须与它自己的
足迹一致。这条检查现在写进了回归脚本（`tests/plate_multi.py`、`tests/multi_probe*.py`）。

## 决策记录：`--arrange 0`，别让 CLI 动我们的摆盘（v0.8.1）

CLI 的 `--arrange` 默认 `auto`：加载模型时会重新排版，把用户摆在 (250,250) 的单件挪到床心。
更隐蔽的后果是重排后床被塞满，多色切片必报
`gcode path conflicts found between WipeTower and 部件` —— 看起来像擦嘴塔的 bug，其实是摆盘被覆盖。

用户既然在 3D 里摆好了，服务端就不要有意见：固定 `--arrange 0`，坐标 1:1 传下去。
验证方式：请求 `x=250` → gcode 多边形 x 区间的中心必须是 250。

## 决策记录：料盘扣重的「总量从打印机来，比例从 gcode 来」（v0.9.0）

做料盘账本时最直觉的做法是「扫 gcode，按工具头算出米数，直接扣」。单色文件这么算是准的
（42 个历史任务实测，和 Orca 自己写的 `; filament used [mm]` 误差 <0.1%），但多色文件
差了 40%：换料时那串「回抽 55 mm / 挤料 55 mm / 分几次补」的序列，Orca 的 per-filament
统计把它算进去了，而我们的「净挤出」（正负 E 相加）把它抵消掉了。两种口径都自洽，
但对不上。

不纠结谁「对」：**总量听打印机的**。Moonraker 的 `print_stats.filament_used` 是挤出机
真实走过的净长度，这是唯一花掉的钱；**分摊比例听 gcode 的**（哪个工具头用了多少，
比例在多色文件上和 Orca 一致到 ±12%）。两者相乘就是每个槽位的扣减量。

配套的两个设计：
- 远端文件名必须带 job id（`<model>-<12hex>.gcode`），否则打印历史接不回本地任务，
  也就拿不到 per-tool 比例 —— 这时退化成「整包记到当前槽位」。
- 记账幂等：Moonraker 的 `job_id` 写进记录里，`/spools/sync` 可以随便点，
  重复的会被跳过（实测第二次 `count=0`）。

## 决策记录：账本用单个 JSON，不用数据库（v0.9.0）

料盘账本的写频率极低（一次打印一条记录，一天几条），读频率高（每次打开页面）。
SQLite 更「正规」，但要引入 schema 迁移、备份、并发写的事务边界，收益不成正比。
最终用一个 JSON 文件 + 临时文件原子替换：
- 掉电最多丢最后一次写入，不会写坏；
- 文件坏了先改名成 `spools.broken-<ts>.json` 备份，再重建空账本（绝不用新数据覆盖旧文件）；
- 记录上限 500 条（`MAX_RECORDS`），料盘和槽位不设限。

如果以后要做多用户/多台打印机共享账本，再换数据库；现在的规模不值得。


## 决策记录：segments.bin 改「按段交错」（v6，v0.9.2）

v5 之前每层在文件里是四段分开的：`[16n 位置][n 类型][n 截面][2n 属性]`。
好处是写入时四块各自 append；坏处全在读取端——这份数据最终要变成 WebGL 的
**每段实例属性**（一条 draw call 画完整层），而 GPU 只认「按段交错」的定长记录。
于是每层都得先在 CPU 侧重排一遍：287 层 × 50 万段，滚到哪重排到哪，
大模型上肉眼可见地卡一下，而且代码里有两条读取路径（v5 的平面、v6 的交错）要各自维护。

改成写入时就按段交错，代价只是 flush 时多一次跨步写入
（`rec[0::20] = pos[0::16]` 这种切片赋值，纯 C 层 memcpy 循环）。

改了格式就必须处理两件事：

- **老任务不能废**：服务端 `_read_layer` 按 `index.version` 判断，v5 及更早读出来
  在服务端重排成 v6 布局再返回，客户端只有一条路径；v5 任务的 bin 文件本身不动。
- **浏览器缓存不能毒**：`/preview/bin` 带 `Cache-Control: max-age=86400`，
  老缓存里的平面分组字节会被当成交错记录读，整层乱码。所以前端请求带上
  `?v=<index.version>`，URL 一变就不可能命中文档缓存。

验证（同一份 gcode，v5 任务 vs 用 v6 重新解析）：

- 数据层：v5 文件按层重排后与 v6 文件**逐字节相同**（10,069,920 B / 503,496 段）；
- 几何层：`tests/validate_preview.py` 独立实现交叉校验，段数偏差 0.00%、长度 0.000%；
- 渲染层：同一机位逐像素比较（3 种显示模式 + 固定视角，6120 格）**最大差 0**；
- 绘制耗时：50 万段 / 287 层，单次 draw ≈ 0.2 ms（swiftshader 软件渲染）；
- 边下边画：限速 2.5 MB/s，覆盖率随下载进度单调上升（37% → 80% → 100%）。


## 决策记录：拐角用斜接，不用方头端帽（v0.10.1 → v0.10.3）

屏幕线是「每段一个四边形」。要让相邻两段在拐点处不露洞，有两种常见做法：

**A. 方头端帽**：每段沿自己方向两头外伸半宽。实现最省事（顶点着色器里两个 `+`），
代价是拐角处两段重叠一块：那块被画两遍，两段的边沿明暗也叠在里面 ——
拐角内侧就会出现一条偏暗的斜缝；转角超过 90° 时，方头还会往轮廓外戳出「耳朵」。

**B. 斜接（miter）**：两侧角点都取「前一段偏移边」与「后一段偏移边」的交点。
两段算出来的角点相同 → 拐点处**共用一整条边**，既不缺口也不重叠，和矢量图里
的 miter join 同义。

选了 B。理由：这个预览要表达的是「走线之间的相邻关系」，方头那块重叠和戳出的
耳朵都是几何上不存在的像素。

**0.10.1 的教训：公式放在着色器里就锁死了自由度。** 斜接长度 = `hw/cos(θ/2)`，
碎段（0.05～0.2 mm）上它越过段子的另一端，四边形翻成「X」；而着色器只看得到
自己这一段和两个邻接方向，不知道邻段有多长，没法截断。0.10.1/0.10.2 只好在
「整段退回方头」（重新引入重叠）和「整体缩短斜接」（横向宽度也被缩掉，碎段拐点
变窄、看着还是细/断）之间来回换。

**0.10.3 的结论：把角点偏移整段搬到 CPU。** 每个拐点只算一次，两侧写同一组
数字（`aNbP/aNbN`，mm），着色器只负责换算成视口单位。这样一来：

- 角点是否是同一个点，由构造保证（两边是同一个世界坐标），投影怎么畸变都不散；
- 截断有全部信息（两段的长度、角度、共享半线宽），可以按段长精确截；
- 偏移拆成「横向满宽 + 沿段进退」，只截沿段那截（0.45×段长，两侧共用系数），
  宽度不动、四边形不翻，代价只是角上一个小斜切（bevel）。

配对仍然是**只在同一层内配**：竖壁上相邻两层的接缝点常常是同一个 XY，跨层配对
会让拐角按层间那条线去斜接。0.001 mm 量化的坐标做 key，20.7 万段约 90 ms。

验证不靠眼睛（`slicer-node/tmp/verify_joint0103.py`，在真实预览数据上跑）：
指标是四边形自交数、相邻两段角点距离、拐点附近名义笔画的缺口/重影比例。
0.10.3 实测：20.7 万段自交 0、缺口 0.97%、重影 1.35%、98.6% 端点走真斜接。


## 0.10.4：拐点角点必须落在角平分线上（修正 0.10.3 的错误假设）

0.10.3 的角点是「横向取满宽 hw + 沿段方向进退 t」：A 用 `nA·hw + dA·t`，
B 用 `nB·hw − dB·t`。当时以为这样两侧端点重合，**这是错的**。

`nA·hw + dA·t` 与 `nB·hw − dB·t` 只有在 t 恰好等于斜接值时才相等；
一旦因为碎段翻面而把 t 缩小，两条边就各自沿**不同方向**（dA 与 dB）平移，
变成两条不相交的平行线——一个四边形收进来，另一个还留在原地，
于是接缝处既出现缝（两条边之间的带子谁也没盖）又出现压边（另一侧叠了两次）。

实测（20.7 万段的真实切片）：抽样 3350 个拐点里 740 个接缝两侧角点不重合（22%），
重影 1.79%，正好对应「线段边缘没有连上」的观感。

**几何事实**：同时满足「两侧横向都是满宽 hw」的点只有一个——两条偏移边的交点，
也就是斜接点。任何为了防翻面而做的收缩都只能沿**角平分线**移动，而沿角平分线
移动 d 距离时横向分量是 `d / L`（L 是斜接长度系数），收缩必然让该侧变窄。即：

- 接缝严丝合缝 ⇒ 两侧共享同一个点 ⇒ 收缩只能是沿角平分线的等比收缩（窄颈）；
- 保满宽 ⇒ 只能各自取自己的交点 ⇒ 接缝必然错开（缝或压边）。

0.10.4 选择**严丝合缝**（要的是「边缘相连」）：
令 `o_σ = σ · b · (hw · min(L,3) · k)`，A、B 算的是同一组数、同一个 float，
屏幕上就是同一个点；k=1 时横向分量恰好 = hw，就是满宽真斜接。
k<1 只出现在碎段上，代价是拐角处一道窄颈，不产生缝也不会叠。

截断规则一并重做：以前是单头 `0.45·len`，把完全正常的 90° 拐角
（sp≈+hw、ep≈−hw、段长 2×线宽）也削窄了几 %；现在三条约束——单头 `0.9·len`
两条，加「两头进退之和 < 0.98·len」一条（后者才是真正翻面的条件），
每次只收紧绝对值大的那一头，收到刚好为止，收缩单调、几遍收敛。

另一处对齐：`wOf()` 与着色器 `width_of()` 逐字一致（无面积数据的 v5 老工程返回
0.45 而不是 0），所以老工程也能走拐点，不再是满地方头。

实测（`ac2ec0e5198a`，20.7 万段 / 20.1 万个拐点）：

| 指标 | 0.10.3 | 0.10.4 |
|---|---|---|
| 接缝两侧角点不重合 | 740 / 3350 抽样 | 5（0.15%，同起点重复段） |
| 重影（两边都盖到） | 1.79% | 0.58% |
| 名义笔画缺失（含窄颈） | 0.90% | 2.68% |
| 自交（四边形翻面） | 0（按旧口径） | 9 / 20.7 万段 |
