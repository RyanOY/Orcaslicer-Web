## v0.11.6 — 2026-11-01

**主题：把 0.11.5 的收缩率补完 —— 切片页能改、摆盘检查按放大后的尺寸算。**

0.11.5 只做到「配置 → 耗材里能设、切片时生效」。用起来还缺两块：

### 1. 切片页「参数覆盖」里搜不到收缩率

覆盖面板只加载**工艺** profile 的 schema（`/profiles/process/<name>`），
耗材级参数（`filament_shrink`、`filament_shrinkage_compensation_z`、温度、回抽……）
在面板里根本不存在，搜「收缩」什么都搜不到 —— 但后端 `overrides` 一直是按 key 路由的，
缺的只是元数据。

现在 `loadSliceSchema()` 合并 **工艺 + 每个耗材槽 + 机器** 三份 schema：
组顺序以工艺为准，耗材/机器的新组补在后面；覆盖值仍是「本次切片」级别。
注意：耗材级覆盖会同时作用于所有槽（面板顶部已写明），各槽不同的值请去配置页设。
切片页右栏的「本次切片」还多了一行 **收缩补偿**：`T4 XY 98% → ×1.020 …`。

### 2. 摆盘检查 / 自动摆盘 / 一键缩放都没算放大

收缩补偿会把模型放大（填 90% 就是 ×1.111），但 `/plate/check`、`/plate/arrange`、
`/plate/fit` 拿到的都是**原始尺寸**的对象，检查说放得下、切出来却出界。

三个接口现在都接受 `filaments[]` + `overrides{}`（前端已带上），服务端用
`_shrinks_of()` / `_with_shrink()` 把 XY 系数折进 `scale`、Z 系数单独存 `__sz`，
于是边界/重叠检查、排布间距、统一缩放比例全部按**切片后的真实尺寸**算。
前端那条提醒也改成「切片尺寸会放大到 X%（检查已按放大后算）」，
并且跟切片页的覆盖值联动。

### 验证

- `tests/ui_shrink_override.py`（真浏览器）：进「3 切片」→ 搜「收缩」命中
  `filament_shrink` / `filament_shrinkage_compensation_z` 两个 number 框；
  改成 95 后右栏出现「1 项 · 收缩率/收缩率 XY」；无 JS 报错。
- `tests/shrink_bounds.py`：同一个模型缩放到「刚好装进 350 热床」，100% 无警告；
  90% 耗材 → `超出热床范围`；切片页覆盖 `filament_shrink=90%` 同样报；
  `/plate/fit` 的 factor 1.000 → 0.938（按放大后占地算）。
- `tests/ui_plate_shrink.py`（真浏览器）：摆盘页加对象、切片槽切到 90% 耗材后，
  警告变成「T4 收缩率 XY 90%：切片尺寸会放大到 111.1%（检查已按放大后算）」。
- `tests/shrink_test.py`（真切片回归）：XY 90% → 34.05×66.27（×1.1126/×1.1119）、
  Z 90% → 53.60、240→267 层，与 0.11.5 一致。

**已知未做**：摆盘 3D 视图里仍按原始尺寸画（几何/拖拽/占地阴影都不跟着放大），
只有检查和右栏数字反映放大后的尺寸。

**部署**：`orca-slicer-node:0.11.6`，8039，health=0.11.6。

## v0.11.5 — 2026-11-01

**主题：耗材收缩率（XY / Z）能设了，而且真的生效。**

### 1. 问题：参数在库里，界面上找不着

`schema/params.json` 里其实早就有 `filament_shrink`（XY）和
`filament_shrinkage_compensation_z`（Z），但：

- `params.json` 从 Orca 源码抽出来时**没有 `cat` 字段**，所有参数只能掉进「其他」组；
- 两个参数都是 `mode: advanced`，在配置编辑页的「常用」视图里被直接过滤掉。

结果就是耗材配置里根本看不到收缩率，更没法填。

### 2. 更麻烦的：写进去了 Orca 也不认

按 Orca 的语义，`filament_shrink = 90%` 应该把模型放大 100/90。实测**不生效**：

| `filament_shrink` 形态 | 切片后 X 尺寸 |
| --- | --- |
| `["100%"]`（基线） | 30.60 |
| `["90%"]` | 30.60 |
| `["50%"]` | 30.60 |
| `"50%"`（标量） | 30.60 |
| `["50"]` / `[50]` | 30.60 |

`strings` 里能查到 `get_matrix_with_applied_shrinkage_compensation`、
`has_same_shrinkage_compensations`，说明补偿在 Orca 里是**摆件时乘到对象矩阵上的**，
headless CLI（`--slice 0`）没有那一步。所以这不是我们参数写错，是 CLI 路径本身不走。

### 3. 做法

1. **展示层**：`app/schema.py` 加 `UI_OVERRIDES`，把两个参数归到「收缩率」分组、
   `mode` 改成 `simple`、补中文说明；`describe()` 还会把这两个 key **强制补进**
   耗材 profile 的参数列表（老 preset 里没写也照样能填，默认 100）。
2. **控件**：`web/form.js` 对「只有一个值的 percents」给数字输入框（50~150，单位 %），
   不再是「逗号分隔的多挤出机 textarea」；回写保持原形态——数组还数组、标量还标量。
3. **补偿自己做**：`app/plate.py` 新增 `shrink_of()` / `_apply_shrink()`，切片拼 3MF
   时按每个对象所用料槽的收缩率做世界轴各向异性缩放（XY 绕包围盒中心、Z 绕底面），
   `overrides` 里的收缩率优先于 profile。「参数覆盖」里改也能生效。
4. **摆盘检查提示**：收缩率不是 100 时，摆盘页会提醒「会放大到 X%，留点余量」——
   边界/重叠检查用的是原始尺寸，不会自动跟着放大。

### 4. 验证

- `tests/shrink_test.py`（真切片）：XY 90% → X 30.60→34.05（×1.1126）、Y ×1.1119、
  Z 不变；Z 90% → Z 48.20→53.60（×1.1120）、层数 240→267、XY 不变。
- `tests/shrink_profile.py`：profile 里存 `["90%"]` + `"95%"` 也生效
  （bbox 34.44×66.66、高 50.53、253 层）。
- `tests/render_shrink.mjs`（最小 DOM 垫片跑 `renderForm`）：常用视图里出现
  「收缩率」分组 + 2 个 number 输入框（默认 100、min 50），改值回写
  `["92%"]` / `"97.5%"` 形态正确。

**部署**：`orca-slicer-node:0.11.5`，8039，health=0.11.5。

## v0.11.4 — 2026-11-01

**主题：摆盘的旋转支持三轴（X/Y/Z）—— 不止原地转盘，能把模型立起来、翻过去。**

### 1. 之前的状态

对象只有 `rot`（绕 Z 的转盘角），加一个「选择底面」写进去的任意朝向矩阵 `m`；
用户能把模型转到某个面朝下，但**没法再绕 X/Y 微调**，也没有地方看到/输入 X/Y 角。

### 2. 这次的设计：角度是状态，矩阵是派生物

- 对象上新增 `rx/ry/rz`，朝向按 `R = Rz(rz)·Ry(ry)·Rx(rx)` 合成；
  落到后端还是老的两样东西：`rot = rz`、`m = Ry(ry)·Rx(rx)`（两者都是 0 时 `m` 置空，
  纯 Z 旋转继续走原来的快路径，旧存档/服务端 `_rot_matrix` 一行没改）。
- **角度不做反解**：填 30 就是 30，按一次 `⟳15°` 就是 +15。之前试过「矩阵→欧拉角」的写法，
  绕世界轴转一下 `RZ` 就漂成 26.565 这种值，输入框会自己变，已放弃。
  只有「选择底面」和旧数据（只有 `rot`/`m`）会分解一次，然后写成角度。
- 万向锁（`ry = ±90°`）不会丢信息：矩阵永远由角度合成，不会出现角度互相吃掉。

### 3. 交互

- 工具栏新增 `X / Y / Z` 轴选择（紧挨 `⟲15°` `⟳15°`，这两个按钮变成「绕选中轴」，
  按住 Shift = 90°）。
- 「旋转」模式拖对象：`Z` 按相对对象中心的方位角转（原来的转盘手感），
  `X/Y` 上下拖（0.6°/px）——把模型立起来最直观。
- 侧栏对象卡片从 4 个数字框变 6 个：`X / Y / 缩放` + `RX° / RY° / RZ°`，三轴都能直接填，
  三个角度清零 = 复位朝向（贴面也能一起清）。
- 绕 X/Y 拖拽时先用包围盒线框、不重建占地凸包（要扫全部顶点会掉帧），松手补一帧完整阴影。

### 4. 验证

- `tests/rot3_math.mjs`：欧拉↔矩阵互转、累加不漂移、`ry=±90` 万向锁、贴面矩阵还原、
  老数据角度化后朝向不变 —— 14 项全过。
- `tests/plate3d_smoke.mjs`：无浏览器 DOM 桩跑 `createPlate3D`，走 `anglesOf/setAngles/
  rotateAxis/resetOrientation`（app.js 真正调的接口）—— 11 项全过。
- 切片端到端：`rot=30` 仍是 240 层、高度 48；`rx=45` / `rx90+rz30` 切片 done。

### 5. 发现一个 Orca 引擎的坑（不是我们的 bug）

把模型绕 X 转到 **88°~90°**（接近完全立起来）后切片，Orca 2.4.2 会报
`found slicing or export error for partplate 1`。对照实验排除了我们的嫌疑：

| 输入方式 | rx=0 | rx=45 | rx=87 | rx=88 / 90 |
| --- | --- | --- | --- | --- |
| 我们烘好坐标的 3MF | ✅ | ✅ | ✅ | ❌ |
| 顶点不动、靠 build item `transform` 让 Orca 自己转 | — | — | — | ❌ |
| 纯 STL 直接喂 `orca-slicer` | ✅ | — | — | ❌ |

同一姿态把 `RZ` 加 1°、或 `enable_support=1`，立刻就能切。所以是引擎在该姿态下
（支撑/悬垂那段代码，日志里 `max_cantilever_dist=7.1e+06`）自己炸，与摆盘坐标无关。
处理：前端在收到这个通用错误时追加一句提示（微调 1° 或打开支撑），并且在
`feature-status.md` 记成已知坑。

## v0.11.3 — 2026-11-01

**主题：折线的「展开方向」改用屏幕空间切线法线 —— 修平视仍然是发丝。**

### 1. 现象（用户报）

0.11.2 之后线宽已经按像素算了，但**平视时走线还是细如发丝**。

### 2. 根因：宽度改了，「方向」还是物理法线的投影

0.11.2 只把**宽度**搬到屏幕空间，展开**方向**依旧是「世界 XY 里的横截面
法线」投影到屏幕上。这条路线在掠射角下会失效：

- 平视看一面墙时，走线的横截面法线几乎垂直于镜头，它的屏幕投影会缩成一条
  **沿着走线自身方向**的线；
- 带宽于是全摊到了线的长度方向上，竖向几乎没有面积 —— 整面墙变成一根根
  细横线，放大后层间还能露出缝；
- 同一个原因也解释了零星的「看得见/看不见」跳变：方向越接近退化，可见面积
  越接近 0，全靠 `dl > 1e-7` 的兜底在撑。

### 3. 修复：方向只由「切线」决定，宽度只由「像素」决定

- 顶点里存的不再是法线角，而是**本段切线角 + 拐点另一侧那段的切线角**
  （`RIB_FLOATS` 9 → 10，多一个 `aNbrt` 属性）；
- 着色器把两条切线分别投影到屏幕上取**屏幕法线**，再相加归一化
  （`p1 + p2` 与顺序无关，所以拐点两侧算出的方向完全一致 → 角点仍是同一个
  屏幕点，不缺口不重叠）；
- 退化兜底分三级：平分线 → 单侧法线（180° 折返）→ 屏幕竖直；带子左右对称，
  方向取反覆盖的区域相同，不会开口；
- 线宽下限 0.7 → 0.6 半像素、逐段实例化路径 `MIN_HALF_PX` 0.45 → 0.60，
  亚像素线不再被光栅器漏成虚线。

### 4. 验证（headless + 像素统计，job 1738e42c5629 / 2f7cf4eabf58）

- 与「体积模式」逐像素对比（体积 = 真立体，作为覆盖的真值）：

  | 视角 | flat 缺失 | 修复前 |
  | --- | --- | --- |
  | 平视 el=0.02 | **0.4 %** | 4.3 % |
  | 斜视 el=0.62 | 0.2 % | — |
  | el=0.30 / -0.25 | 0.3 % / 0.2 % | — |

- 平视竖扫的墨迹 run 中位数：**2 px → 93 px**（发丝 → 实心带），
  发丝占比 73.2 % → 38.2 %（剩下的多是物体轮廓边缘的 1 px 过渡）；
- 26 万段的大任务走逐段实例化路径，同样通过（无 WebGL 报错，覆盖正常）。

## v0.11.2 — 2026-10-31

**主题：折线几何改为「屏幕空间等宽」—— 修平视时走线没有厚度、以及一段粗一段细。**

### 1. 现象（用户报）

- 平视（镜头接近水平）时，走线看起来没有厚度，像一张纸；
- 有些线段呈锥形：一端粗一端细。

### 2. 根因：线宽是在**世界坐标**里定死的

0.11 的折线三角带，CPU 直接写成「中心点 ± 法线 × 半线宽」的世界坐标顶点，
着色器只做投影。于是：

1. **透视拉细**：一条线段两头的深度不同，世界坐标里固定 0.45 mm 的宽度在
   屏幕上就不是同一个像素数 → 近端粗、远端细（用户看到的「锥形线」）。
2. **平视塌成发丝**：线宽方向躺在 XY 平面里。当墙面正对镜头、相机又接近水平
   （`el≈0`）时，这个偏移方向几乎沿视线 → 投影长度趋近 0 → 整条线变成一条
   1 px 发丝，甚至看不见（用户说的「没有厚度」）。老实现还有斜接 `sec(θ/2)`：
   拐角处会额外伸出一截，短段的伸长约到 40% 段长，看起来同样是「一头粗一头细」。

### 3. 修复：把「方向」和「宽度」拆开

- CPU 只负责**方向**：每个折线角点算一个单位法线角（入段/出段左法线的归一化
  和 = 角平分线），顶点里存 `(中心点 x, y, z, 法线角, ±半线宽 mm)`。
  拐点两侧读到的是**同一组数**，所以屏幕上仍是同一个点，接缝不缺口、不重叠。
- 着色器负责**宽度**：把「中心点」和「中心点 + 一个半线宽」都投影，取差值的
  **方向**（丢掉长度），再乘回 `半线宽 × uProj / w` 的像素数。于是每个顶点离
  中心线的距离恒等于半个线宽（像素），与视角、深度、朝向无关：
  - 任何角度都等宽（锥形线消失）；
  - 平视时仍是 1~2 px 的实带（不再是零面积侧影）；
  - 线宽依旧随缩放走（`uProj/w` 里的 w 变了，像素宽跟着变），放大不会出层缝。
- 法线正对镜头（投影退化）时，兜底成屏幕竖直方向 —— 否则 `normalize(0)` 会让
  那段线整条消失。
- 不再乘斜接 `sec(θ/2)`：屏幕上从角点沿法线走半个线宽，乘与不乘只差「尖角 vs
  圆角」，1~3 px 线宽下看不出来；保留它反而破坏了等宽。

### 4. 验证（25.9 万段 Dyson 任务，单层，放大到 dist=120）

| 指标 | 0.11.1 | 0.11.2 |
| --- | --- | --- |
| 平视 `el=0.02` 发丝线（≤2 px）占比 | 1.4% | **0.4%** |
| 平视 + 正对墙（az=4.82）发丝占比 | 6.3% | **1.5%** |
| 12 个方位角走线像素总和 | 1 248 125 | 1 260 416（+1.0%） |
| 俯视 `el=1.55` 线宽分布 p5/p50/p95 | 5 / 5 / 7 px | 5 / 5 / 7 px（不变） |

改动只在 `viewer/index.html`（`buildRibbons` 发顶点 + `VS_RIBBON`），
后端与 API 契约不变。

## v0.11.1 — 2026-10-31

**主题：修「累积 / 全模型视角整屏空白」—— 折线渲染失败后把空当成画过了。**

### 1. 现象

0.11.0 上线后，切到「累积」或「全部」视角，画面里一条走线都看不到
（底板网格还在，模型位置一片空）。缩小/放大、切换层都一样空白。

### 2. 根因

`drawRibbons()` 的缓存逻辑有个状态机错误：

```js
const n = buildRibbons(loB, hiB, ppm);
ribbonKey = key;                    // ① 先把 key 记成「已建好」
if (n > RIB_VERT_CAP) {             // ② 顶点超上限
  ribbonN = 0; return false;        // ③ 这一帧退回逐段四边形（能画出来）
}
...
if (ribbonN <= 0) return true;      // ④ 下一帧：key 相等 → 不重建 → ribbonN 还是 0
                                    //    → 返回 true，却一个顶点都不画
```

第 ④ 步不再走实例化回退，于是**第一帧有、第二帧起全空**。累积视角段数是
单层的几十倍，必然超上限，所以这个视角必现；单层视角不超上限，看起来正常。

### 3. 修复

- 建失败时把 `ribbonKey` 清空（并记进 `ribbonSkip`），下一帧老老实实走
  实例化路径；`ribbonN <= 0` 一律返回 `false`。
- 折线顶点上限 32 万 → 90 万（≈32 MB），全模型预算 30 万 → 70 万段：
  13.9 万段的累积视角现在直接用连续折线（86.8 万顶点，1 次 draw call）。
- 超过上限时先按可见段数估顶点量（≈6.4 顶点/段），提高合并力度
  `coarse` 再建一次，而不是立刻退回逐段四边形（碎线/掐腰的来源）。

### 4. 验证

| 场景 | 修复前 | 修复后 |
| --- | --- | --- |
| 25.9 万段 累积（连画 2 帧） | 第 1 帧 836k 顶点、第 2 帧 **0** | 868k 顶点 / 868k 顶点 |
| 25.9 万段 全部（连画 2 帧） | 第 1 帧 1.56M、第 2 帧 **0** | 1.56M / 1.56M（实例化回退） |
| 50.3 万段 累积 / 全部 | 第 2 帧起 **0** | 2.76M / 3.02M 稳定 |
| 画布亮像素占比（单层/累积/全部） | 11.3% / 0% / 0% | 11.3% / 16.2% / 19.5% |

## v0.11.0 — 2026-10-31

**主题：预览从「每段一个四边形」改成「按折线建模」—— 墙体是一条连续的带子，
不再是拼接的砖块。**

### 1. 现象与定位

同一份 OrcaSlicer 导出的 GCode，在 SimplyPrint 里是连续折线，在我们这里是一串
离散碎线。先把「数据」和「渲染」分开查：

- 解析出来的数据是干净的：某任务 L150 外墙 346 段、按坐标首尾相接率 95%，
  剩下的 5% 都是真正的空驶/U 形分离，段长中位数 0.38 mm、线宽 0.42 mm。
- 也就是说 GCode 与解析没问题，问题在**几何建模方式**：每一条 G1 生成一个
  独立四边形，四边形两头各外伸半个线宽（方头）。
- 两个必然的失效点：
  1. **段长 < 线宽**（该任务 57% 的段都短于 0.42 mm 线宽）。斜接长度算出来
     比段长还长，只能被 `0.9·段长` 夹住 → 每个关节被掐细一次，墙看起来像
     一串珠子。实测 31% 的关节「沿段方向可视长度 < 半线宽」。
  2. **亚像素**：缩到全模型时一段只有零点几像素，一个四边形经常整个落在
     像素中心之外被丢弃 → 直接变成虚线。
- 另外方头让每段都外伸半宽，短段密集处互相覆盖成「砖块堆」，轮廓呈锯齿。

### 2. 做法：先组装折线，再画折线

`viewer/` 里新增一条渲染路径（`buildRibbons` / `drawRibbons` / `VS_RIBBON`）：

1. **组装**：同层 + 同类型 + 「上一段终点 == 下一段起点」的连续段合成一条
   Polyline；G0、ΔE=0 空移、E 回抽、换层、换类型都是硬边界（解析器里
   `path_open` 显式关闭，不再依赖坐标巧合 —— 这也顺手修掉了 Z-hop/原地点抽
   之后被误判为连续的老问题）。
2. **化简**：段内点距 < max(1.15×线宽, 1.6 px)、弦偏差 ≤ 0.6 px、转角 < 25°
   才合并 —— 远看自动合并成长线，近看保留细节，形状偏差始终小于一个像素。
   这一步把「段比线宽还短」的结构性前提消掉了。
3. **斜接**：每个角点只算一次偏移，前一段的出口和后一段的入口引用同一组
   float，所以关节在屏幕上是同一个点，构造上不可能有缝或重影。斜接太长/太尖
   （sec > 1.9 或沿段伸长超过 0.4×段长）时退化成**斜切**，再用一个楔形三角
   把外侧缺口补满 —— 宁可多一块重叠，也不掐细。
4. **亚像素保底**：线宽下限 1.25 px（按当前缩放换算回 mm 写进几何），
   缩到全模型也是一条连续的带子。
5. 整层仍是一次 `drawArrays`，顶点数 9 float/点（x y z side | type attr vact
   aeff | hw），着色依据/类型过滤/隐藏类型全部还是 uniform，切换不重建几何。
   段数超过 45000（整模型一览）时自动退回原来的实例化四边形路径。

### 3. 解析器侧

按同一套规则显式维护折线，并把结果写进索引，便于核对：

| 字段 | 含义 |
| --- | --- |
| `path_count` | 全文件折线条数 |
| `retract_splits` | 因 E 回抽（ΔE<0）切分开的次数 |
| `dedupe_skipped` | 与上一点重合（<1 µm）被跳过、但**未**打断折线的点数 |
| `layers[].paths` | 该层折线条数 |

25.9 万段的任务：11581 条折线、2350 次回抽切分、0 个被去重的重合点。

### 4. 验证

- 同一机位 A/B（`old.html` 逐段四边形 vs 新路径）：中心线覆盖率两者都 100%，
  但新路径的像素是旧路径的严格子集（旧路径多出来的 2.7% 全是方头在拐角处的
  鼓起），即形状不变、毛刺消失。
- 几何层面：掐腰的关节 31% → 0（化简后关节处两侧引用同一角点）。
- 一帧耗时：4289 段三层 → 9.9 ms 建几何 + 一次 draw call；19920 顶点。

## v0.10.4 — 2026-10-31

**主题：拐点两侧角点改成「角平分线上的同一个点」—— 接缝从几何上就不可能错开，
0.10.3 的缝和压边一起消失。**

### 1. 0.10.3 错在哪

0.10.3 的角点是「横向满宽 hw + 沿段方向进退 t」：A 用 `nA·hw + dA·t`，
B 用 `nB·hw − dB·t`。当时以为这样两侧端点一定重合，其实只有 t 恰好等于斜接值
时才相等。一旦碎段翻面、t 被截小，两条边就各自沿**不同方向**（dA 与 dB）后退，
变成两条不相交的平行线：一边收进去、一边没动，于是接缝处要么露缝、要么叠两层。

实测 20.7 万段工程：**抽样 3350 个拐点，740 个接缝两侧角点不重合（22%）**，
重影 1.79%。这就是「线段中心连上了、边缘没连上」看到的东西。

### 2. 做法：一个点

几何上只有斜接点同时满足「两侧横向都是满宽」，而任何防翻面的收缩都只能沿
角平分线走（横向分量 = `d/L`，必然变窄）。所以干脆两边都写成

```
o_σ = σ · b · ( hw · min(L, 3) · k )
```

A 的退出端点和 B 的进入端点算的是同一组数字、写进同一个 float —— 屏幕上就是
同一个点，缝和压边从几何上消失。`k=1` 时横向分量恰好 = hw，就是满宽真斜接。
`k<1` 只在碎段上出现，代价是拐角处一道窄颈（不产生缝，也不会叠）。

### 3. 截断规则重做

以前是单头 `0.45·len`：普通 90° 拐角 sp≈+hw、ep≈−hw、段长 2×线宽时就贴着上限，
**完全正常的拐角也被削窄几 %** —— 这也是缺口的一部分来源。现在三条约束：

1. `|sp| ≤ 0.9·len`（起点角点别越过本段大半个身子）
2. `|ep| ≤ 0.9·len`
3. `|sp − ep| ≤ 0.98·len`（两侧长边真翻面的条件）

每次只收紧绝对值大的那一头、收到刚好为止；收缩单调 → 只会让相邻段更宽松，
三遍收敛。

### 4. 顺手对齐

`wOf()` 与着色器 `width_of()` 逐字一致（无面积数据的 v5 老工程返回 0.45 而不是 0），
**老工程现在也走拐点**，不再是满地方头（v5 实测 48.9 万个拐点、0 个折返退化）。

### 5. 实测

| 指标 | 0.10.3 | 0.10.4 |
|---|---|---|
| 接缝两侧角点不重合 | 740 / 3350 抽样 | 5（0.15%，同起点重复段） |
| 重影（两边都盖到） | 1.79% | 0.58% |
| 名义笔画缺失（含窄颈） | 0.90% | 2.68% |
| 四边形自交 | 0 | 9 / 20.7 万段 |

- 另一个工程（25.9 万段、37.5 层、0.16 mm）：角点不重合 704 → **0**，重影 2.29% → 0.53%。
- 像素级：高倍渲染 91.9 万笔画像素里 13 个针眼（0.001%）。
- 满宽占比：86.7% 的拐点 k≥0.9；k<0.3 的 1.29 万个里 1.10 万个落在 <0.2 mm 的碎段上。
- 耗时：20 万段 194 ms、26 万段 355 ms（一次性建表；拐点只在放大到线宽 ≥1.8 px 时才建）。

## v0.10.3 — 2026-10-31

**主题：拐点角点改由 CPU 一次算清、两侧共用同一组数 —— 碎段不再「断开」，也不用
退回方头去堵洞。**

### 1. 0.10.2 留下的两个尾巴

0.10.2 把拐点线宽统一成了 `(wA+wB)/2`，斜接能用了，但**碎段的斜接会翻领结**：
斜接长度 = `hw/cos(θ/2)`，段长只有 0.05～0.2 mm 时这个长度早就越过段子的另一端，
四边形自交成一个「X」。0.10.2 的办法是这类拐点整段退回方头端帽 —— 代价是方头
沿自己方向外伸半宽，两段在拐点互相插进去，就是用户看到的「端点两头交叉重叠」。
实测 20.7 万段的工程里 **62% 的端点**都走了方头，等于大半个模型还在用老画法。

### 2. 做法：把斜接拆成「横向 + 沿段」

角点偏移可以拆开看：`o_σ = σ · ( n·hw + d·t )`，`t = hw·L·(角平分线·d)`。

- **横向那截 `n·hw` 永远是满线宽**。0.10.2 的截断是整体缩短，横向也跟着缩，
  碎段的拐点就变窄、覆盖不到名义笔画 —— 换了个样子继续「细/断」。
- **只有沿段那截 `t` 会翻领结**（它把角点推过本段另一端）。按段长把它截到
  `0.45 × min(段长)`：一段两头最多各占 0.45，和仍小于 1，四边形必然不自交。
  代价只是角上一个小斜切（bevel），宽度和连续性都不动。

截断系数两侧取同一个（`min` 两段的限值），A、B 的角点沿各自的偏移边等比后退 ——
实测比「两侧各截各的」露缝少一半（缺口 1.79% → 0.97%）。

**全部搬到 CPU**：`ensureNeighbors()` 按坐标配对后，每个拐点算一次，写成
`aNbP/aNbN`（每段 8 个 float，两侧各一个 mm 偏移），着色器只做 mm→视口的换算。
两段读到的是同一组数字，角点在屏幕上是**同一个点**（投影畸变也不影响这条，
因为两边是同一个世界坐标），不再有「各算各的、差半个线宽」的可能。

### 3. 验证

- 20.7 万段工程（job `ac2ec0e5198a`）：**98.6% 的端点走真斜接**（方头只剩 1.4%，
  0.10.2 是 62%）；四边形自交 **0** 个；名义笔画缺口 0.97%、重影 1.35%
  （0.10.2 光栅化重影 6.35%）。
- 37.9 万段老格式（v5，job `5c670017d6c1`）：自交 **0**，缺口 0.20%、重影 1.68%。
  顺手修好：v5 任务以前**完全不走拐点**（宽度守卫把非交错布局直接挡掉了）。
- 渲染层：900 px 视口、12 mm 视野（≈75 px/mm，深缩放）数「笔画内部的针孔」
  —— **0 个**；45 mm 视野下 0.034%，与旧版一致（那是正常的线间距空隙）。
- 性能：`ensureNeighbors` 20.7 万段约 90 ms、37.9 万段约 370 ms，一次性；
  每段多 32 B（20.7 万段 ≈ 6.6 MB）；单帧绘制 0.1–1.3 ms。

### 4. 顺手修的

- 底栏「本层」在顶层（只有移动、没有挤出的那一层，`t = 0`）显示成 `—`，
  `tests/ui_check.py` 因此一直报「底栏有未填字段」—— 现在照实显示 `0 s · 0 mm`，
  UI CHECK 从 FAIL 变 OK。

## v0.10.2 — 2026-10-31

**主题：短线段（碎段）的拐点 —— 消掉「断开」和「端点两头交叉重叠」。

### 1. 两个根因，都在拐点的半线宽上

斜接要成立，前提是**同一个拐点两边算出来的半线宽必须一样**。0.10.1 里每段用的是
自己横截面积推出的线宽，而碎段（弧线上的 0.05～0.2 mm 小段、悬垂墙上的锯齿）截面积
跳得最厉害 —— 用真实数据量出来：8.8% 的拐点两侧线宽差 > 0.02 mm，2% 差 > 0.05 mm，
最大 0.10 mm（接近四分之一线宽）。宽的那侧压过去 → 端点两头**交叉重叠**；窄的那侧
退回来 → 同一个拐点两侧各留一道**缺口**，也就是「短线段断开」。

第二个：转角超过限值（>≈138°）时整侧退回方头端帽，两段的方头在拐点互相插进去。
实测 140° 拐角上两段各自伸出 0.36 mm、重叠面积占到局部 66%～144%。

### 2. 修法

- **拐点线宽统一**：CPU 侧按 `(wA + wB) / 2` 算一个「共享线宽」写进 `aNbW`
  （每段 2 个 float），两段读到的是同一个数 → 角点是同一个点。屏幕侧只做
  `px = mm × 投影缩放`，所以透视下也保持一致。
- **超限转角改成「截断斜接」**：长度封顶在 3 倍半宽，但角点仍是同一个（共享边
  不变，只是外侧尖角削平一小块），不再退回方头 —— 交叉重叠消失。
- **碎段退回方头**：相邻两段里有一段短于一个线宽时，斜接角点会伸到比整段还长的
  位置，四边形直接翻成「领结」（真实数据里 6.6% 的段是这样，全是 0.07 mm 级的
  锯齿段），看着就是一个 X。这类拐点两段都退回方头（宽度符号编码在 `aNbW` 的
  正负号里，天然一致）。用覆盖率光栅化验证：该区域自交 2/7 → 0，缺口 ~0%。

### 3. 验证

- 真实数据 66228 个同层拐点：两侧角点误差 **0 µm**（原来 12.5% 超 5 µm，p99 540 µm）。
- 光栅化覆盖率（0.006 mm/像素）：正常走线区重影 64% → 6.35%，碎段区自交 0。
- `tests/ui_check.py` 像素覆盖率与 0.10.1 一致（1.07% / 6.21% / 9.29%）。

## v0.10.1 — 2026-10-31

**主题：预览里相邻走线在拐点处「边接边」—— 换成真正的斜接（miter）拐角，缺口和重叠一起消掉。

### 1. 问题：中心线连上了，边缘没连上

屏幕线模式下每段是一个实例化的四边形。以前为了不让拐角露洞，做法是把四边形沿
自己方向两头各外伸半宽（方头端帽）：两段的方头在拐点叠一块，洞是补上了，但

- 叠出来的那块被画两遍，两段的边沿明暗也叠在里面 → 拐角内侧一条偏暗的斜缝；
- 转角超过 90° 时方头往轮廓外戳出「耳朵」，比实际描边还宽。

### 2. 做法：两侧都取偏移边的交点

顶点着色器里新增 `jointOff(uIn, uOut, side, hw)`：把「进方向」和「出方向」各自
的法向偏移线求交，得到角点。相邻两段算出来的角点必然相同 → 它们在拐点处**共用
一整条边**，既不缺口也不重叠。斜接长度 `hw·√(2/(1+cosθ))`，超过 2 倍半宽
（≈138° 转角）就整侧退回方头端帽（两段一致，仍不缺口，只是角上多叠一点）。
180° 折返时公式退化，直接走方头。

邻接关系 `aNb`（每段 4 个 float：前段方向、后段方向的单位向量）在 CPU 侧按坐标
配「上一段终点 == 本段起点」，**只在同一层内配** —— 竖壁上「这层最后一笔的终点」
和「下一层第一笔的起点」常常是同一个 XY，跨层接起来转角就按层间那条线算了。
9.5 万段约 95 ms，一次算完，之后每帧只读属性。

### 3. 什么时候开

`joinOn = 线条模式 && 线宽 ≥ 1.8 px && 当前视图段数 ≤ 8 万`。细线时那点角度差
根本看不见，全模型一览时少读 4 个邻接属性更划算。

### 4. 验证

- 几何层：用与着色器逐行相同的公式在 Node 里复算 18 个转角（0°–175°）：
  缺口 0.00%、重叠 0.00%、共边误差 < 1e-14（`slicer-node/tmp/verify_join.js`）；
- 数据层：9.5 万段里 91,230 段接得上前段、91,121 段接得上后段、87,688 段两头都接；
- 渲染层：浏览器实测 5 px 线宽下，笔画内背景空洞 0 个；方头版的「耳朵」
  消失（整帧描边像素 18,799 → 18,775），单帧绘制 0.3–1.3 ms。

## v0.10.0 — 2026-10-31

**主题：预览反映机器的真实加减速 —— 转角掉速、长直段才冲满，速度/加速度两列按 Klipper 限速回放算。

### 1. 为什么原来「和机器不一样」

预览的每段是一条独立线段，端帽外伸半宽、颜色取 gcode 的 `F`。但机器上 `F` 只是
**上限**：Klipper 的 lookahead 会把每段规划成梯形速度曲线 —— 转角前先减速、出角再
加速，短段根本到不了指令速度。所以「指令速度」着色看到的是一条条恒速线，
和实际打印的节奏完全不是一回事。

### 2. 做法：把规划器搬到解析器里

`app/gcode.py::_velocity_profile` 对整条挤出路径做了三件事：

1. **拐角限速**：`v_j = scv·√((1+cosθ)/(1−cosθ))`（θ 为转角）。直线 → 由巡航速度封顶，
   90° → `scv`，折返 → 0。语义与 Klipper 文档的 `square_corner_velocity` 一致，
   参数从 `M205 J` / `SET_VELOCITY_LIMIT SQUARE_CORNER_VELOCITY` 读，缺省 5 mm/s。
2. **梯形规划**：前向扫「这段能爬到多快」→ 反向扫「到下一段前刹得住吗」→ 再前向
   传一遍。加速度取 `M204 S` / `SET_VELOCITY_LIMIT ACCEL`（缺省 3000）。
3. **段内再规划**：两端速度已知时长段中间可能还有匀速平台，用
   `vp = √((2aL+v₁²+v₂²)/2)` 反解，避免把「两端都停的 20 mm 长线」算成 0.005 mm/s。

输出每段的**平均速度**与**有效加速度**（`|v₂²−v₁²| ÷ 2L`），
uint16 落盘：v7 每段 24 字节（新增偏移 20 速度×100、22 加速度）。

### 3. 前端

- 新增两个着色依据：**实际速度**、**实际加速度**（渐变表 256 行，按 `attr_ranges` 映射，
  不占 attrs 表）。
- `uColorMode` 扩展成 0 类型 / 1 属性表 / 2 真实速度 / 3 真实加速度；
  每段多两个 `UNSIGNED_SHORT` 实例属性 `aVact`/`aAeff`。
- 旧的「速度」保留为指令速度（`note` 里写清了区别），底板网格强制按类型上色。

### 4. 验证

- `tests/validate_preview.py` 扩到 v7：字节数、属性下标、以及**物理可行性** ——

## v0.9.6 — 2026-10-31

**主题：预览样式固定为「线条 + 强明暗」，并修掉线条模式两个老毛病 —— 线宽不跟缩放、转折处断开。**

### 1. 线宽必须跟缩放同步

`VS_FLAT` 里的半宽被钳在 `[0.8, 4.5]` 设备像素。这条钳位是「屏幕线」时代为了防
细线消失/粗线爆填充率留的，但它和物理缩放是矛盾的：

| 距离 | px/mm | 物理线宽 | 物理间距 | 旧钳位后线宽 | 结果 |
| --- | --- | --- | --- | --- | --- |
| 60 mm | 23.1 | 10.4 px | 9.7 px | 9.0 px（被 MAX 切） | 放大后线间距露出缝隙 |
| 25 mm | 55.4 | 24.9 px | 23.3 px | 9.0 px | 缝隙 14 px，非常明显 |
| 300 mm | 4.6 | 2.1 px | 1.9 px | 1.6 px（被 MIN 顶住） | 缩小时线比间距粗 → 挤压成一团 |

改成 `MIN_HALF_PX = 0.45` / `MAX_HALF_PX = 400`：线宽严格 = 物理挤出宽度 × pxPerMm，
只留一个亚像素保底防止光栅洞。实测 60 mm / 25 mm 两个距离，实心区域里背景像素占比
0.0%（钳位时代 25 mm 处约 60%）。

### 2. 转折处连续

每段是独立四边形、两头是平头（butt），拐点处两段只在一个点上相接，
斜角（弓箭形近似出来的 135° 弯）外侧就留下一个楔形缺口 —— 放大看就是「断成一节一节」。

- 沿线方向两头各外伸一个半宽（方头端帽），90° 以内的转折缺口被直接填平；
- 横截面明暗（中间亮两侧暗）按线宽淡入 `vEdgeK = clamp((halfPx-0.6)/1.6, 0, 1)`：
  细线（<2.4 px）完全不做明暗，否则每条线都是「亮心 + 两条黑边」，
  挨在一起看着就是断续的斑马纹；线够粗（>4.4 px）才把强明暗的立体感打开。

### 3. 默认样式

- `tubeMode` 默认 `off`（线条），`shadeLevel` 默认 `2`（强明暗）；
- 顶栏按钮/滑杆仍可改，改动记在 `localStorage`；顶栏按钮文案在加载时同步（不会再显示成「体积」）。

实测（`bb3c1c285d48`，俯视 el=1.25，全部层）：线条模式平均亮度 93.7、覆盖 207 510 px；
体积管模式 64.5 → 线条更亮更清楚，符合「细线最清楚」的定位。

## v0.9.4 — 2026-10-31

**主题：预览整体偏暗，俯视视角尤其暗；根因是漫反射权重给太大，而俯视看到的几乎全是丝侧壁。**

实测同一任务 `bb3c1c285d48`（0.16 层高，细管几何），只改着色器：

| 视角 | v0.9.3 平均亮度 | v0.9.4 | 说明 |
| --- | --- | --- | --- |
| 俯视 el=1.35 | 57.3 | 83.3 | 之前最暗的视角 |
| 斜视 el=0.55 | 53.3 | 81.3 | |
| 平视 el=0.2 | 60.4 | 82.3 | |
| 仰视 el=-0.3 | 85.9 | 95.5 | 各视角差从 33 收窄到 14 |

原因：旧式子是 `shade = 0.46 + 0.52*diff`，diff 是法线与光的余弦。
扁截面压扁后，一个像素里绝大多数是**丝的侧壁**（法线水平，主光几乎打不到），
diff≈0 就落到 0.46 的地板；而俯视时视野里几乎全是侧壁（顶面只有 0.16 mm 高、
几十万段铺满屏），所以「俯视特别暗」。仰视看到的是朝上的面，diff 高，反而正常。

改法（只动 FS_TUBE / 屏幕线着色，几何与布局不变）：

- `shade = 0.84 + 0.14*diff + 0.04*wrap` —— 大部分是本体色，只留一小截随光变化，
  接近 Orca 的平涂 + 轻微明暗；任何朝向都不会整体变黑。
- 朝上/朝下系数 `0.90 + 0.10*ao`（原 0.70+0.30）；层缝压暗 22% → 15%，
  底色抬到 0.85。层界靠「顶面亮 / 贴下层暗」的小反差 + 层缝线，仍然看得清。
- 屏幕线模式中心-边缘系数 0.68 → 0.84，细线不再整体发灰。

层界可辨识度没有丢：压扁截面 + 层缝仍在，只是不再用整体压暗来换层次。

## v0.9.3 — 2026-10-31

**主题：层高 0.16 的切片「预览看不出层」，根因是段数预算把体积管判死了。**

用户反馈：同一份模型切 0.16 层高，预览走线糊成一片、层与层分不开。
对比两次任务的段数：

| 任务 | 层高 | 层数 | 段数 | 旧版几何 |
| --- | --- | --- | --- | --- |
| `fb7e37d709f9` | 0.2 | 230 | 409 823 | 体积管 ✅ |
| `bb3c1c285d48` | 0.16 | 287 | 499 387 | 屏幕线 ❌ |

`pickTier()` 用的是**整份文件**的段数，门槛 `tubeOk = segs <= 450000`。
0.16 层高把段数顶到 49.9 万，自动模式直接判死、永远退回「屏幕线」——
而屏幕线是纯色四边形，没有任何明暗，叠起来就是一张糊片。层高本身没问题，
是同尺寸模型多出的 20% 层数跨过了那道门槛。

改动：

- **预算按「当前视图真正要画的段数」算**：单层视图 = 当前层 + 下面两层，
  累积 = 0..当前层，只有「全部」才是全量。细管 160 万段 / 球冠 20 万段。
- **只提交可见层**（`visibleByteRange()`）：以前不管什么模式都把整份实例流丢给
  GPU、靠顶点着色器丢弃；50 万段的任务在单层视图里也要跑 50 万个实例。
  现在单层只提交 ~4300 个。这也是球冠能放开预算的前提。
- **挤出丝截面按层高压扁**：以前是直径 0.4+ mm 的正圆柱，层高 0.16 时上下层互相
  插进去 60% 以上；现在截面是「宽 = 挤出线宽 ×1.15、高 = 层高」的椭圆，
  顶面在层顶、底面在层底，法线按 1/压扁比修正，每层正好占满自己的层高。
- **层缝压暗**：竖直外壁上所有层的侧法线完全一样，光照明暗一模一样 —— 只靠光照，
  一整面墙就是一条纯色。层底往上 35% 的范围压暗 22%，等于给每层画一条暗边。
- **屏幕线也加横截面明暗**（中心亮、两侧暗，底板网格除外），兜底几何不再是纯色块。
- 球冠网格从 6 环降到 4 环、棱数 6 → 8（压扁后 6 边看得出折面）。

验证（同一机位 `dist=110 / el=0.55`，1400×900，读回 framebuffer 统计）：

| 任务 | 几何 | 亮像素 | 平均亮度 |
| --- | --- | --- | --- |
| 0.16 任务（修前） | 屏幕线 | 386 478 | 96.3 |
| 0.16 任务（修后） | 细管 | 216 196 | 53.4 |
| 0.2 任务（对照，一直正常） | 细管 | 215 109 | 54.8 |

修后的 0.16 任务与一直正常的 0.2 任务在同一机位下**覆盖率与亮度基本一致**
（216 196 px / 53.4 vs 215 109 px / 54.8），确认它已经回到体积管那条路径。

## v0.9.2 — 2026-10-31

**主题：预览数据改成「按段交错」（格式 v6），客户端不再自己重排。**

之前每层在 `segments.bin` 里是 `[16n 位置][n 类型][n 截面][2n 属性]` 四段分开存的。
这套数据最终要当成 WebGL 的**每段实例属性**用（一条 draw call 画整层），
所以每一层都得先在 CPU 侧重排成 20 字节交错才能上传：287 层 / 50 万段，
滚到哪重排到哪。大模型卡顿、首屏空白、以及「某些层不显示」这一串毛病的根就在这。

改动：

- **写入即交错**：`gcode.py` 的 `flush()` 直接按段写 20 字节定长记录
  （位置 4×Float32 | 类型 | 截面 | 属性），`index.version` 升到 6。
  层内仍按类型桶排序，`ranges` 不变，类型过滤只是 `seek(offset + start*20)`。
- **老任务不废**：`_read_layer()` 按版本判断，v5 及更早读出来在服务端重排成 v6
  再返回，客户端只有一条读取路径（`layoutInterleaved = version >= 6`）。
- **缓存穿透处理**：`/preview/bin` 是 `max-age=86400`，老缓存里的平面分组字节
  会被当成交错记录读成乱码，所以前端请求带 `?v=<version>`。
- 测试同步：`tests/validate_preview.py`、`check_attrs.py`、`render_preview.py`
  的二进制解码按版本分支（v6 走切片、v5 走平面分组），两代任务都能校验。

验证（同一份 gcode，旧 v5 任务 vs v6 重新解析）：

| 检查 | 结果 |
| --- | --- |
| 文件字节 | v5 按层重排后与 v6 **逐字节相同**（10,069,920 B / 503,496 段） |
| 独立交叉校验 | 段数偏差 **0.00%**、挤出总长偏差 **0.000%**（`validate_preview.py`） |
| 属性对齐 | `check_attrs.py` 通过（外墙/内墙/支撑各自的线宽与速度分布一致） |
| 渲染一致性 | 3 种显示模式 + 固定机位，6120 格最大像素差 **0** |
| 类型过滤 | `?types=` 返回的记录与全量按类型筛出的记录逐字节一致（v5/v6 两条路径） |
| 绘制耗时 | 503k 段 / 287 层，单次 draw ≈ 0.2 ms |
| 边下边画 | 限速下覆盖率 37% → 80% → 100% 单调上升 |

## v0.9.1 — 2026-10-31

**主题：热床 35℃ 的锅不在耗材配置——槽位里根本没选那份耗材。**

现象：用户选的是 JAYO PLA（`data/profiles/filament/jayo-pla.json`，`cool_plate_temp=48`），
切出来 `M140 S35`。

两个独立原因：

- **切片根本没用 jayo-pla**。job 的 `filament` 是 `generic-pla,generic-pla,generic-pla,generic-pla`：
  摆盘槽位里存的是上一次的默认值（第一份耗材 = Generic PLA，`cool_plate_temp=35`），

  都不是合法值，会被静默退回 Cool Plate（35℃）；`High Temp Plate` 取 `hot_plate_temp`，

- **摆盘页新增「热床板」下拉**（低温板/高温板/纹理PEI/工程板/超粘板），

- **MMU 槽位铺满**：MMU 机器按 ACE 实际槽数（4）铺槽位，不再只铺 1 个；

- **料盘绑定真正参与切片**：`syncFilamentsFromSpools()` 把「这槽装的哪卷」的切片配置

- **新对象默认落在装了料盘的槽**：`defaultExtruder()` 优先用 ACE 当前槽，其次第一个
  绑了料盘的槽；否则又会出现「T4 装了 JAYO，对象却全是 T1」。
- **检查栏告警**：对象用的工具头没装料盘、而别的槽装了时明确提示（会用空槽的耗材配置，
  热床温度也可能不对）。
- 版本号 `/health` 升到 `0.9.1`（镜像 `orca-slicer-node:0.9.1`）。

**主题：3D 摆盘「第一次进去不显示模型」。**

- **`refresh()` 不再被 `if (gl)` 挟持**：首次进摆盘时 GL 上下文可能还没建，
  旧代码直接跳过绘制；现在没上下文就先建，再画。
- **网格懒上传**：`loadMesh` 在上下文不可用时会把网格缓存成「有顶点、没 vao」，
  之后永远画不出来。抽出 `ensureUpload()`，`draw()` 每次顺手补齐。
- **首帧尺寸兜底**：切到摆盘那一瞬间画布 `clientWidth=0`，`resize()` 原样返回，
  首帧就画在 300×150 的默认缓冲里（看不见）。现在尺寸为 0 时下一帧重试，
  `go("plate")` 也改成「立刻画 + rAF 再画 + 150 ms 兜底画」。
- **上下文丢失自愈**：监听 `webglcontextlost/restored`（移动端切后台、同时开多个
  WebGL 页面是常见诱因），恢复后重建程序/床面、清空网格 vao 并重画；另加
  `visibilitychange`/`pageshow` 重画。
- **网格加载失败会重试**：原来 `.catch()` 静默吞掉，失败一次就永远是空的；
  现在 `refresh()` 会补拉缺的网格，失败打 `console.warn`，并隔 1.5 s 自动重试（最多 3 次）。
- **网格下载不再可能永久卡住**：抓到过 `await r.arrayBuffer()` 响应已 200 却永不返回的
  情况（请求甚至没发到服务端）。改成「`fetch` 流式读取 15 s 超时 → XHR 兜底 20 s」。
- **「＋ 摆盘」直接跳到摆盘页**：原来只在模型库弹个 toast，很容易被当成「点了没反应」。
- 排障接口：`window.__plate.debug()`（上下文/画布尺寸/网格 vao）与
  `window.__plate.probe()`（立刻重画并统计非背景像素，验证「真的画出来了」）。
- 工具：`make web` 热更前端（会自动 `chmod a+rX`）。踩坑记录——NAS 上源文件是
  `700` + uid 984，直接 `docker cp` 进容器（uid 1000）会读不到，浏览器报
  `ERR_CONTENT_LENGTH_MISMATCH` 整页白屏。

## v0.8.2 — 2026-10-31

**主题：「参数明明改了却不生效」——表单把布尔值读反了。**

- **修复所有布尔开关显示错误**：Orca preset 里布尔存成字符串 `"0"`/`"1"`，
  前端用 `Boolean(value)` 判断，`Boolean("0") === true`，于是每个「关闭」的开

## v0.8.1 — 2026-10-30

**主题：把「切片结果和摆盘对不上」这一类问题收干。**

- **修复「两个不同的部件切成两个一模一样的部件」**
  多耗材工程 3MF 原先把网格拆到 `3D/Objects/object_N.model` 再用 `<component p:path>` 引用。
  OrcaSlicer 2.4.2 解析 component 时**按 `objectid` 在全局 id 空间里找、根本不看 `p:path`**，
  每个外部文件里的对象都叫 `id="1"` → 互相覆盖 → 所有对象拿到同一份网格。
  改法：网格全部内联进主 `3dmodel.model`（每对象 id 唯一），挤出机仍写在 `model_settings.config`。
  验证：同一盘两部件，多边形从「都是 268.2×96.6」变成 195.3×200.3 / 137.8×137.7。

- **修复摆盘位置被 Orca 丢弃**
  CLI 的 `--arrange` 默认是 `auto`，加载模型时重新排版：摆在 (250,250) 的单件会被挪到床心 (175,175)。
  更麻烦的是重排后床被塞满，双色切片必报 `gcode path conflicts found between WipeTower and 部件`。
  改法：`build_argv()` 加 `--arrange 0`。
  验证：单件 x[177.5,322.5] 精确命中；双色 285 层成功。

- **修复 profile 数字数组导致 CLI 拒载**
  `load_from_json: ... invalid json array for cool_plate_temp`。编辑器保存的用户 profile 里写成了
  `[48]`，Orca 只认 `["48"]`。改法：`profiles.clean()` 加 `_orca_scalar()`（读写两端都过），
  `slicer._flake()` 写盘前再兜一层。

- `/health` 增加 `version` 字段，便于确认「现在跑的是不是修复版」。
- **项目文档整体重写**：根 README（现状/架构/功能矩阵）、`docs/feature-status.md`（分模块清单 + 验证方式）、
  `docs/changelog.md`（本文件）、`docs/api-contract.md`（改为 as-built）、design-notes 补三条决策。
- **部署收尾**：`docker commit` 固化 `orca-slicer-node:0.8.1`，改由 compose 接管
  （`restart: unless-stopped`），停掉 8038/8037 两个旧实例，清理 0.7.5 及更早的 26 个镜像标签和 32 个历史容器。
  收尾后跑了一次双部件回归（两个部件轮廓 205.5×210.8 / 145×145，位置 1:1，300 层），确认新容器行为与热补丁一致。
- 部署：`chmod 644` 后 docker cp + restart。又一次因为文件权限 700 导致容器启动即退（记在 README）。
